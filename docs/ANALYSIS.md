# 逆向分析信息

本文记录对 FNIRSI DSO-153 原厂固件的静态分析与实机标定结果：分析对象、方法、
存储器布局、启动与各子系统的结构、补丁点的依据、每条关键结论的证据，以及尚未
解决的问题。Phosphor 补丁中出现的每一个硬编码地址都应能在这里找到出处；修改
补丁前先来这里核对置信度。

分析对象：原厂 APP v1.6，文件 `APP_DSO153_V1.6_20240427.bin`，191232 字节，
加载基址 `0x08007000`。该镜像版权归 FNIRSI，本仓库不分发；本文只描述合法持有
副本的分析结果。

证据强度分级（全文适用）：

- **已验证**：静态分析与实机行为一致；
- **静态**：仅由反汇编或数据扫描得出，未经实机确认；
- **推断**：由间接证据推得，实现中不得当作事实使用。

## 3. Flash 布局

| 范围 | 内容 | 长度 |
|---|---|---|
| `0x08000000..0x08005FFF` | IAP 引导程序（USB MSC） | 24KB |
| `0x08006000..0x08006FFF` | 设置页数据：版本、语言、亮度、校准 | 4KB |
| `0x08007000..0x08035AFF` | 原厂 APP | 191232 字节 |
| `0x08035B00..0x0803FFFF` | 空闲 → 补丁代码区 | 42240 字节 |

要点：设置页数据独立于 APP 镜像，版本串就在这一段，`set_version.py` 的定位策略
是"在 24KB 之后搜索 `V1.6\0\0` 并回溯冒号"。补丁镜像（R36 为 18692 字节）追加
在 `0x08035B00`，上界 `0x08040000` 由构建强制。

（`0x08007394`，值 `0x2000A580`），与堆基址共用——说明原厂没使用堆。

一个重要的历史教训：`0x2000A528` 起的 64 字节窗口曾被当作"设置结构"标定过一轮
字段，全部作废——该窗口实为 UI 状态区，且与按键队列重叠。真实设置结构在
`0x2000001C`。

## 5. 启动链与主循环

| 地址 | 作用 |
|---|---|
| `0x08007000` | 向量表（`main` 将其写入 VTOR） |
| `0x08007364` | 复位向量 |
| `0x0801A788` | `main` |
| `0x08016E74` | `SystemInit`（FPU、PLL） |
| `0x08016F40` | 外设与显示初始化 |
| `0x0801A7B0` | 主循环 |

主循环每轮串行调四个任务，实测周期约 200ms（约 5Hz 刷新）：

```
0x0801A7B0  bl 0x08009500    按键与 UI 事件
0x0801A7B4  bl 0x0800B544    菜单与设置
0x0801A7B8  bl 0x080128F0    模式调度
0x0801A7BC  bl 0x08008EE0    电源管理与 UI 渲染   ← 补丁 hook 替换点
0x0801A82E  b  0x0801A7B0
```

这个 200ms 周期是补丁架构的第一约束：命令解析进中断、键码注入限速，都源于它。

## 6. IAP 与 USD

### 6.1 IAP 模式

关机状态下按住 `AUTO` + 电源 + 插 USB，引导程序进入 USB MSC 模式，主机看到
`AT32 Msc iap` 磁盘。该磁盘是虚拟 FAT（2048 字节/扇区 × 4095 扇区，报告 8MB），
**不对应 Flash 线性映射**，从中读不出引导程序或 APP 内容。引导程序独立于 APP，
补丁不触碰，这保证刷写失败后 IAP 仍然可用。

### 6.2 EOPB0 不可靠

EOPB0 位于 USD `0x1FFFC010`，低两位按数据手册编码 SRAM 配置（00=512KB，
01=448KB，10/11=384KB）。但实测两次直接读取得到不同值（`0xFFFFEF10` 与
`0x0000BD10`），且 nEOPB0 不构成反码——AT32 的 USD 需经 Flash 控制器读取，普通
内存读不构成可靠访问。因此"标称 384KB"不能当作可用 SRAM 的证据，一切以 §8.3
的写入实验为准。

## 7. USB/CDC 栈

官方 AT32 USB device 库 + 补丁胶水的结构见 [USB_STACK.md](USB_STACK.md)，此处只
列逆向相关结论：

- 48MHz USB 时钟无法从 300MHz PLL 整除得到（/6 = 50MHz，偏差 +4.17%），代码改用
  HICK + ACC（修剪窗口 7980/8000/8020，以 OTG1 的 SOF 为基准校准）——已验证
  （枚举成功且时钟链状态量可读）；
- OTGFS1 中断号 67，向量 `0x0800714C`，补丁改指 `usb_irq`；
- 端点：EP0 控制 / EP1 批量 IN+OUT / EP2 中断 IN，均 64B；
- 官方库为单包在途模型（`g_tx_completed` 闸门），吞吐上限由它与全速批量 64B
  包长共同决定。

## 8. 采集链路与数据源

### 8.1 原始采样

`FUN_08019458` 配置 ADC1 → DMA1_CH0 → `0x2000025D`，传输量 `0x4000`（16384），
样本 8 位。当前写位置 = `0x4000 − DMA1_CH0CNT`（读出函数 `FUN_080194E8`）。
缓冲是环形且被持续覆盖，由此产生协议的三条固有语义（详见 PROTOCOL.md §8.1）：
帧是发送时刻的滚动快照、帧间不保证连续、起始时刻算的校验不可作完整性判定。

### 8.2 屏幕波形

`0x2000425E`，301 点，随显示刷新更新，与屏幕点列一一对应。独立于环形缓冲，
发送窗口短，校验通常成立。

### 8.3 可用 SRAM 上界：48KB 的实测推导

用"写入未映射地址 → 精确总线错误（PRECISERR）→ 故障桩记录 BFAR → 软复位 →
主机读现场"的方法，对三处地址做写入实验（两个固件版本结果一致）：

| 写入地址 | 结果 |
|---|---|
| `0x2000B800..0x2000BFFF` | 正常（补丁变量区就住这里） |
| `0x2000C000` | 写入即掉线复位 |
| `0x2003A800` | 写入即掉线复位 |

三点夹出结论：可用上界 `0x2000C000`（48KB）。副作用：这类复位后 CRM 只报
POR/NRST、RAM 被清，"崩溃→复位→读回进度"的诊断方式在这台机器上不成立。

这个结论推翻了"SRAM 标称 384KB、可以把帧缓冲放顶部"的推断，也直接导致整屏
截屏链路（常驻帧缓冲 153600 字节 + Flash 存图两条路都差 10 万字节以上）被整体
放弃，改为推屏时直发的画面流。

## 9. 按键系统

| 对象 | 地址 | 说明 |
|---|---|---|
| 队列缓冲 | `0x2000A53E` | 20 项环形 |
| 读 / 写指针 | `+0x14` / `+0x15`（`0x2000A552/53`） | 入队出队共用 |
| 出队函数 | `0x080188A5` | 返回键码，`0xFF`=无 |
| 入队函数 | `0x080188E9` | r0=队列地址，r1=键码 |
| 处理函数跳转表 | `0x0801F39C` | 14 项，`表[键码−1]` |

键码 1–14 的含义见 [PROTOCOL.md](PROTOCOL.md) §8.5。键码 10 实测无可辨识现象
（推断为保留值或无面板对应的通路）。

"上"键处理函数 `0x0800AE20` 的结构值得记录：两级 `tbh` 分派，先按 MODE 选中项
（`0x20004FCC`），再按底栏子选择（设置结构 `+0x0E`）。这解释了设备参数模型是
"选中项 + 子选择 + 值"三元组，也解释了为什么注键改档必须先选对底栏项——
R36 之前垂直档位直设失败，根因就是子选择编号**从 1 起**，`+0x0E=3` 是时基不是
档位。

## 10. 设置结构

基址 `0x2000001C`（静态：52 处引用；实机：字段值与面板显示一致）。已标定字段：

| 地址 | 字段 | 取值 | 证据 |
|---|---|---|---|
| `+0x01`（`0x2000001D`） | 垂直档位 | 0..8 | 原厂加/减档代码（`0x0800AE74` 递增、`0x0800996E` 递减）+ 实机面板核对 |
| `+0x03`（`0x2000001F`） | 探头倍率 | 0/1 | 差分扫描与面板一致 |
| `+0x0D`（`0x20000029`） | 时基索引 | 0..23 | 边界 `cmp #23` + 24 档字符串表 |
| `+0x0E`（`0x2000002A`） | 底栏选中项 | 1..7（从 1 起） | 二级 `tbh` 前的边界比较 + 实机 |
| `+0x59`（`0x20000075`） | 信号发生器波形类型 | 0..13 | `0x0800AA68` 递增后调 `0x080164E8` 分派 14 段生成 `0x20004574` 表 |
| `+0x66`（`0x20000082`） | 设置页行选择 | 0..4 | 递减代码 |

**+0x59 的纠错记录**（防再犯）：它曾被当作垂直档位，实机证伪——底栏显示
2V/div 时 `+0x01=7` 而 `+0x59=8`；把 `+0x59` 从 8 改 0 后抓屏，波形与文字毫无
变化；`0x080164E8` 按它分派生成的 301 点表是信号发生器波形（exp/正弦等）。另
一教训：`0x080164E8` 内部调 `sin` 写波形表，从渲染钩子里调用它会破坏绘制状态、
UI 错位——**钩子里不要调它，也不要调原厂按键处理函数**。

垂直档位的正确改法（R36 起，命令 `0x0D` 复刻原厂链路）：
`+0x01 = 目标 → 0x08008754(目标) → 推 UI 事件 3、1`。`0x08008754` 按索引 `tbb`
分派 10 段，每段写 `0x4002xxxx` GPIO 切前端衰减/增益——只写字段不调它，档位
数字变了波形幅度不变。上限 8：原厂加档到 5V/div 停止，9..12 档设备走不到，
越界索引会落进未定义的 `tbb` 分支。

实机验证（R36，200Hz/3.8Vpp 方波，`phosphor_vtest.py`）：九档全部落到目标，
未超屏的 1V/2V/5V 三档 `峰峰 × mV/div` 恒定，偏差 ≤5%。判据提醒：不能用"峰峰
随档位单调递减"验证——高灵敏档饱和，峰峰反而递增，早期脚本因此误报过。

## 11. 渲染与 UI 路径

| 函数（助记名） | 地址 | 说明 |
|---|---|---|
| `push_band` | `0x08008E64` | 推送当前区域；全镜像 13 处 `bl` 调用全在渲染任务 |
| `fill_rect` | `0x0800E73C` | `(x1,y1,x2,y2,color)` |
| `putpixel` | `0x0800E680` | 写当前窗口缓冲 |
| `drawtext` | `0x080102F0` | 字号 `0x0C/0x10/0x14` |
| `draw_char` | `0x080109A4` | `tbb` 按字号分派 ASCII 字库 |
| 位图绘制 | `0x0800EA48` | 2bpp，关于页 logo |
| 页面组成表 | `0x08017196` | UI 页面号 → 绘制单元 id 序列（画面流重绘照抄此表） |

`push_band` 无参数，区域经窗口结构（§4）传递；序言 4 字节
（`push {r7,lr}` + `sub sp,#8`）恰好放得下一条 `b.w`，函数体首条指令覆写 `r0`——
这两个性质让 4 字节跳板无需保存寄存器。窗口值推屏前写入、推屏后缓冲即释放，
所以取帧数据必须读推屏前的窗口。

界面资源（调色板 `0x08035850`、三档中文字库、三档 ASCII 字库、关于页指针表
`0x080215FC/0x08021600/0x08021640`、菜单表 `0x08021B74`、时基/档位字符串表等）
的完整清单与结构见 [UI_PATCH.md](UI_PATCH.md)；语言号 `0x20001C67`（1..8）、
主题号 `0x20001C6A`。改写关于页指针表即可把自定义串送进原厂渲染路径（`hand/`
的实验实现验证过该结构可写）。

## 12. 标定工具族

`tools/host/` 里有一组为逆向服务的工具，方法各异，供复现与扩展标定：

| 工具 | 方法 |
|---|---|
| `phosphor_scan.py` | 观察模式：设备侧手动操作，工具只读轮询，报告稳定变化的字节（首选，不注入） |
| `phosphor_probe.py` | 分步差分：提示操作 → 前后各读一遍设置结构 → 打印真变化的偏移 |
| `phosphor_sramdiff.py` | 全 SRAM 稳定差分：注键前后各连读三遍，只留"三次稳定且变化"的地址 |
| `phosphor_keys.py` | 遍历"选中项+按键"组合，确认原厂改档到底写哪些字节 |
| `phosphor_live.py` | 对比"只写字段"与"走固件命令"的派生状态差异 |
| `phosphor_writeonly.py` | 验证只写字段不会切前端衰减（实机结论的复现脚本） |
| `phosphor_vtest.py` | 档位增益实测：k = 峰峰 × mV/div 恒定性判据 |

注键探针的三个已知干扰：MODE 选中项未知时按键作用到别的参数；端点夹持截断差
值；反向复原不保证回基线。所以观察模式优先。

## 13. 诊断与 HardFault 设计

原厂 HardFault 向量是 `b .`（死机即假死）且无看门狗，出问题只能拔电池。补丁的
故障桩补上了整条诊断链：

1. `fault_stub`（向量 `0x0800700C`）记录 CFSR/HFSR/MMFAR/BFAR + 栈帧寄存器到
   `0x2000BF00`，写 6 字摘要到 `0x2000BF60`（跨冷启动保留），软复位；
2. 复位原因快照在 `0x2000BF40`（CRM 标志，`0x40023874`：bit26 NRST / bit27 POR /
   bit28 SW / bit29 WDT / bit30 WWDT / bit31 LOWPOWER）；
3. 栈水印（`0xA5A5A5A5` 填充）给出峰值；`stack_base` 来自 `0x08007394` 字面量，
   `stack_top` 来自向量表首字；
4. 同一上电周期 3 次故障内自动复位，第 4 次停住——防止无限复位循环。

PC 定位规则：`≥ 0x08035B00` 补丁代码；`0x08007000..0x08035AFF` 原厂 APP。
内存探测（命令 `0x08` + `--probe`）利用同一机制判定地址是否映射，注意探测未
映射地址本身就会触发复位，需逐地址进行。

## 14. 证据汇总表

| 结论 | 置信度 | 证据 |

| 主控 AT32F435CCT7，256KB Flash，300MHz | 高 | Info block、PLL 寄存器、USB 枚举 |

| 主循环周期约 200ms | 高 | 实测；与刷新率、键码限速互证 |
| 按键队列 `0x2000A53E`，20 项 | 高 | 入队/出队函数 + 注入实机行为 |
| 设置结构 `0x2000001C`；+0x01/+0x03/+0x0D/+0x0E 字段 | 高 | 52 处引用 + 边界比较 + 实机面板核对 |
| `+0x59` 是信号发生器波形而非垂直档位 | 高 | 改写无效果实验 + 生成函数分派分析 |
| 垂直档位必须调 `0x08008754` 切前端增益 | 高 | R36 九档实测（k 恒定，偏差 ≤5%） |
| EOPB0 直接读不可靠 | 高 | 两次读数不同、nEOPB0 非反码 |
| ADC 环形缓冲 16384 点 @`0x2000025D` | 高 | DMA 传输数量 + 样本宽度 |
| 页面组成表 `0x08017196`；页面 1/5/6/7 不重建 | 高 | 抓屏实验（0 块/叠画现象） |
| 键码 10 无可辨识功能 | 中 | 实测无现象 |
| 可用 SRAM 为什么只有 48KB | 未解 | 与 EOPB0 标称矛盾，机制未知 |

## 15. 未解问题

1. **上界成因**：48KB 与标称 384KB/512KB 的差距无法解释——实装更小还是高位
   SRAM 未使能未知。工程结论不受影响：`≥0x2000C000` 一律当不可访问。
2. **设置结构残缺字段**：`+0x1` 相邻的 0..8 索引语义、耦合方式等未标定；垂直
   档位字段虽已标定，`0x08008754` 的 10 段分派与 9 档的对应细节未逐一核对。
3. **触发点对齐**：协议不上报触发位置，原始帧与屏幕波形的时间关系未定量。
4. **键码 10**：功能未知。
5. **IAP 引导程序**：未分析内部结构，只确认其 MSC 行为与区域独立性。
6. **EOPB0 正确读法**：经 Flash 控制器读取的流程未实现，当前以实测代替。
