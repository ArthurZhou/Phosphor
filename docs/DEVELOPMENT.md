# 二次开发指南

本指南面向要修改补丁代码、扩展协议或调整界面资源的开发者，目标是能独立完成：
理解架构 → 搭好环境 → 复现构建 → 通过自检 → 做出修改 → 验证发布。协议细节见
[PROTOCOL.md](PROTOCOL.md)，USB 实现见 [USB_STACK.md](USB_STACK.md)，界面资源改写
见 [UI_PATCH.md](UI_PATCH.md)，补丁点地址的逆向依据见 [ANALYSIS.md](ANALYSIS.md)。

## 1. 架构总览

```
                ┌────────────── 原厂 APP（不动结构）──────────────┐
                │  main 主循环（约 200ms/轮）                      │
                │   ├─ 按键与 UI 事件任务                          │
                │   ├─ 菜单与设置任务                              │
                │   ├─ 模式调度任务                                │
                │   └─ 电源管理与 UI 渲染任务 ←─ bl 被替换为 hook  │
                │  push_band（区域推屏）←─ 入口 4 字节跳板 img_hook│
                └─────────────────────────────────────────────────┘
                        │ 主循环上下文                │ 推屏时刻
                ┌───────▼────────── 补丁代码 ──────────────────────┐
                │ hook(): 冷启动 → usb_poll() → 原任务 → 绘制修饰  │
                │ phosphor_usb.c: 初始化、命令解析(OUT 中断)、     │
                │                 组帧发送(IN 中断)、故障捕获      │
                │ img.c: 画面流（推屏时逐块直发，不落地）          │
                │ 官方 AT32 USB 库: 控制器/端点/标准请求           │
                └─────────────────────────────────────────────────┘
                        │ USB CDC（EP1 批量 IN/OUT，64B）
                ┌───────▼────────── 主机（tools/host/）────────────┐
                │ phosphor_proto.py 帧解析 / GUI / CLI / 诊断工具  │
                └─────────────────────────────────────────────────┘
```

三个设计决定决定了整个代码形态，改动前必须理解：

1. **命令解析在中断里，不在主循环**。主循环一轮约 200ms，放主循环里响应太慢；
   因此命令在 CDC OUT 中断上下文逐字节解析，发送也在 IN 中断推进。
2. **键码注入在主循环上下文**。设备按键队列的入队/出队共用读写指针，跨上下文
   并发会损坏队列，所以补丁只留一个字节的待注入槽位，主循环每轮取走一个——
   相邻键码间隔必须大于约 200ms（工具统一 240ms）。
3. **补丁不调用会破坏渲染状态的原厂函数**。历史上从钩子里调用原厂"应用设置"
   类函数导致过 UI 错位（那个函数实际是绘制路径里的正弦表生成）。新钩子只允许
   调用确认过调用约定与副作用的函数。

## 3. 获取构建输入

两样东西不在仓库里，构建前必须就位：

1. **官方 USB 库**（ArteryTek AT32F435_437 库的 USB 相关部分）：

   ```bash
   python tools/build/at32lib/fetch.py
   ```

   脚本走 GitHub API 逐文件下载并做最小体积校验，防止截断文件混入。每次构建
   前流水线会重新施加本项目需要的局部修改（`patch_lib.py`：描述符字符串、CDC
   名义波特率），所以重新 fetch 不会丢配置。

2. **原厂镜像**：放到 `firmware/vendor/APP_DSO153_V1.6_20240427.bin`
   （191232 字节）。获取途径与真伪校验（长度、首字、复位向量）见
   [RELEASING.md](RELEASING.md)。该文件版权归 FNIRSI，不入库。

## 4. 构建环境

| 组件 | 要求 |
|---|---|
| clang / ld.lld / llvm-nm / llvm-objcopy / llvm-size | 需支持 `arm-none-eabi` 目标 |
| Python | 3.10 及以上 |
| capstone | 静态自检的反汇编 |
| bash | 流水线脚本（Windows 用 Git Bash） |

补丁代码是裸机环境：**不链接 libc、libgcc、compiler-rt**，没有启动代码、堆和
异常处理。需要延时、内存搬运、整数运算时自己实现；避免触发 `__aeabi_*` 辅助
函数和 64 位除法。

## 5. 构建与自检

```bash
PHOS_VER=V1.6SI bash tools/build.sh R36
# 产物：firmware/PHOS_V1.6R36.bin
```

| 参数 | 含义 |
|---|---|
| `R<N>`（唯一位置参数） | 修订号，决定产物文件名；缺省 `R0` 为开发构建 |
| `PHOS_VER` | 设备显示的版本串，最长 6 字符 |
| `THEME_PRESET` | 主题预设，默认 `phosphor2` |
| `SARASA_FONT` | Sarasa 字体路径（仓库不带字体） |

流水线八个阶段，任一阶段失败立即终止：

| 阶段 | 动作 | 失败含义 |
|---|---|---|
| 0 | `patch_lib.py` 修改官方库 | 描述符/波特率没改上 |
| 1 | 编译全部翻译单元 | 代码或配置错误 |
| 2 | 链接（`ld.lld -T tools/fw/link.ld --gc-sections --no-rosegment`）、出符号表与二进制 | 段定义错误 |
| 3 | 校验段布局：`.data` 不低于 `0x2000B800`、`.bss` 末端不越过 `.fault_rec`、故障区不越出 `0x2000C000` | SRAM 布局越界 |
| 4 | 校验 256KB Flash 边界 | 补丁区溢出 |
| 5 | `patch.py` 施加钩子/向量/追加代码 | 原内容校验不匹配 |
| 6 | 改写版本串 + `verify_patch.py` 静态自检 | 自检失败，**不得刷写** |
| 7 | 套用主题、替换字形 | 主题缺失中止；字体缺失仅告警 |

静态自检的检查项数量随实现演进（以构建输出为准），覆盖内容：

- hook 入口的分支目标置 Thumb 位且等于原任务地址；
- 补丁变量区与原厂栈不重叠，不越过 `0x2000C000`；
- 主循环钩子、OTGFS1 向量、HardFault 向量均指向补丁区且置 Thumb 位；
- `push_band` 序言未被破坏（跳板完好）；
- 栈字面量与 `stack_base` 一致，初始 SP 保持 `0x2000B580`；
- 补丁代码内的绝对地址全部落在合法区域（PC 相对寻址按 `Align(PC,4)` 规则解读）。

输出末行出现"静态检查全部通过"才允许刷写。

## 6. 补丁机制

### 6.1 补丁点清单

`tools/patch.py` 修改以下位置；每处在改写前核对原内容，不匹配则跳过并告警
（完整地址依据与置信度见 [ANALYSIS.md](ANALYSIS.md)）：

| 位置 | 原内容 | 改为 | 作用 |
|---|---|---|---|
| `0x0801A7BC` | `bl 0x08008EE0` | `bl hook` | 主循环渲染任务入口 |
| `0x0800DEBE` | `bl 0x0800EA48` | `bl hook_about` | 关于页 logo |
| `0x08008E64` | `push {r7,lr}; sub sp,#8` | `b.w img_hook` | 推屏跳板（画面流） |
| `0x0800714C` | 向量表第 67 项 | `usb_irq` 地址（Thumb 位） | OTGFS1 中断 |
| `0x0800700C` | 向量表第 3 项 | `fault_stub` 地址（Thumb 位） | HardFault 捕获 |
| `0x0800C424` | `movw 0xBDF7` | `0x29A7` | 卡片未选中色 |
| `0x0800C2F6` 等 5 处 | `bl 0x0800E94C` | 双 `nop` | 移除立体装饰条 |
| `0x0802F544` | 4bpp 卡片模板 459 字节 | 清零 | 卡片扁平化 |
| `0x08035AFF` 之后 | 空闲 | 追加补丁二进制 | 代码载体 |

可用命令行开关关闭单项修改做对照实验：`--no-vector`、`--no-fault`、`--no-ram`、
`--no-about`、`--no-img` 等，另有 `--hook-site`、`--about-site`、`--irqn` 改目标。

注意：`0x0800D70A` 与 `0x0800D8A6` 的条纹是声光页的音量/亮度滑条，**不是**装饰，
移除会弄坏功能页。

### 6.2 入口与调用约定

被替换的是一条 `bl`，主循环依赖它的返回地址。因此 `hook()` 以普通 C 函数返回
原任务（编译器的 `push/pop lr` 保证 `lr` 正确）；**不能**用尾调用 `b` 转入原任务，
否则 `lr` 被改写，主循环回不去。所有跳转目标必须置 Thumb 位（`| 1`），否则
Cortex-M4 切去 ARM 状态立刻 HardFault。

### 6.3 冷启动与栈水印

补丁没有启动代码：`.data` 搬运、`.bss` 清零由 `phosphor_cold_start()` 在首次
`usb_poll()` 时做，靠双字魔数（`PHO1`/`USB!`）判定是否已执行，之后每轮调用都是
空操作。同一函数铺设栈水印（`stack_base` 到当前 SP 之间填 `0xA5A5A5A5`，上界留
128 字节不碰存活帧）。故障记录区只在上电时清零，热复位保留现场。

### 6.4 发送与接收

发送状态机由 `tx_hdr/tx_src/tx_n/tx_sent/tx_sum/tx_active/tx_seq` 构成：
`tx_start()` 组帧头、算校验、**当场**提交首包（首包不能等中断，否则永远发不出）；
`tx_pump()` 在 IN 完成中断按 64 字节边界推进，帧尾清 `tx_active`。`tx_active`
置位时 `tx_start()` 直接返回——同一时刻只有一帧在途，连续模式的续帧在
`phosphor_cdc_in()` 里完成。两者都只在 USB 中断上下文运行，无需关中断。

命令解析（`cmd_exec()`）在 CDC OUT 中断逐字节处理；带参数命令用待决标志 + 参数
缓冲，参数允许跨 OUT 包。参数接收期间不接受新命令。

### 6.5 画面流

`img_hook.S` 装在 `push_band` 入口：复刻被替换的 4 字节序言（`push {r7,lr}` /
`sub sp,#8`），调 `img_send_band()`，再跳回 `0x08008E68` 函数体（函数首条指令
覆写 `r0`，跳板不必保存调用者寄存器）。区域参数读全局窗口结构
`0x2000A568`（x/y/w/h 半字，`0x2000A578` 缓冲指针），按 `8 + w*h*2 ≤ 4096` 切行。

安全边界缺一不可：未武装立即返回；窗口与指针先做 `0x20000000..0x2000C000` 范围
校验；每包 30ms 超时；读 IPSR 判中断上下文（中断里直接返回，否则 USB 完成中断
进不来）；先置 `img_busy` 再查端点空闲（防 OUT 中断插入导致帧交错）；预算递减
到 0 自动解除。

`img_serve_redraw()` 在主循环钩子里武装后按 UI 页面号查原厂 `0x08017196` 处的
页面组成表，把该页绘制单元依次排进 UI 消息队列，保证一次抓图是当前页的完整画面。
这张表照抄原厂，不要增减——曾补投过一个底栏 id，结果菜单页凭空多画出五张参数
卡片。

### 6.6 故障捕获

`fault_stub` 是 `naked` 函数：全程不用栈、只用 r0–r4，地址全部 `movw/movt` 立即数
构造（不用 `ldr =imm`，避免字面量池被自检反汇编误判）。记录 CFSR/HFSR/MMFAR/BFAR
与异常栈帧到 `0x2000BF00`，另存 6 字摘要到 `0x2000BF60`（跨冷启动保留），然后
写 `SCB->AIRCR` 的 `SYSRESETREQ` 软复位；本上电周期第 4 次故障起停在原地。

### 6.7 存储器布局不变量

| 不变量 | 原因 |
|---|---|
| 初始 SP 恒为 `0x2000B580` | 原厂栈完整性 |
| 补丁变量区 ≥ `0x2000B800` | 在 SP 之上，与栈隔离；塞进栈区会挤掉 AUTO 键最深调用链，表现为连按两次 AUTO 死机 |
| `.bss` 末端 < `0x2000BF00` | 不覆盖故障记录区 |
| `.fault_rec` 固定 `0x2000BF00` | 故障入口用立即数寻址，构建期校验一致 |
| 补丁代码 ≤ `0x08040000` | 256KB Flash 上界 |
| 向量/跳转目标置 Thumb 位 | Cortex-M4 只跑 Thumb |
| 命令解析不回主循环 | 主循环 200ms 太慢 |
| 新钩子函数放独立段 + `link.ld` 中 `KEEP` | `--gc-sections` 会回收无引用段 |

## 7. 协议与主机工具

新增命令的完整登记要求（命令表、长度表、版本兼容说明、主机侧常量与解码）见
[PROTOCOL.md](PROTOCOL.md) 第 11 节；上位机各模块与打包方式见 [HOST.md](HOST.md)。
新命令从 `0x11` 起分配（`0x09`–`0x0C` 是回收段，`0x0D`–`0x10` 已占用）；设备对
未知命令静默，新旧版本可以共存，但主机必须给无响应命令设超时。

## 8. 界面资源

主题调色板、字形替换、关于页与菜单裁剪全部只改数据不改绘制代码，工具、预设与
约束见 [UI_PATCH.md](UI_PATCH.md)。所有改写工具必须：先校验原值、保证幂等
（同一镜像重复执行无二次破坏）、失败时跳过并告警而不是写半截。

## 9. 仿真与测试

两层验证，都不需要碰真机：

1. **主机侧仿真**：`--simulate` 用 `SimulatedSerial` 按协议生成数据，GUI/CLI/
   bench 均支持，用于界面、解析逻辑与回归。

2. **画面流离线验证**（`tools/test/`）：把 `img.c` 编成 wasm32，用 node 驱动，
   跑的是真代码：

   ```bash
   bash tools/test/run.sh
   ```

   流程：`img_test_wasm.c`（窗口替身 + USB 桩）与 `img.c` 同编 → `img_run.js`
   推送十余个矩形（含 320/208 宽混排）→ 字节流落盘 → `img_check.py` 用生产解析
   器还原并逐像素比对。覆盖：未武装零输出、块描述、4096 上限、校验、序号、预算
   递减、非法窗口拒绝、页面号投递序列（1/5/6/7 必须为空）。不覆盖 USB 时序、
   真实窗口结构、带宽——这三项只能上实机。

修改画面流代码后必须重跑本测试；改补丁主体后以静态自检 + 仿真 + 实机三步验证。

## 10. 版本与发布

版本命名 `PHOS_V1.6R<N>`：基线版本（V1.6）+ 本项目修订号；设备显示串由
`PHOS_VER` 独立指定（≤6 字符，`S` 前缀），与文件名修订号不一一对应。修订号在
功能变化时递增；同一源码换 `PHOS_VER` 重建不算新修订。

发布步骤、附件规范、产物检查清单与依赖获取见 [RELEASING.md](RELEASING.md)。

## 11. 贡献流程

1. 从 ANALYSIS.md 核对涉及的地址与置信度，确认没有把"推断"当事实使用；
2. 改代码，遵守第 6 节的不变量；
3. `bash tools/test/run.sh`（若动了画面流）+ 重新构建确认静态自检通过；
4. 仿真验证后上实机验证，记录测试条件（输入信号、固件版本、观察手段）；
5. 同步更新受影响的文档（PROTOCOL/HOST/ANALYSIS/USAGE），四份主文档（README/
   USAGE/DEVELOPMENT/ANALYSIS）中的版本号、命令、地址要保持一致；
6. 提交时说明：改了什么、为什么、怎么验证的。
